# M1: результат проверки и тестовый backend

Дата: 6 октября 2026 года. Проверен commit `cb8dd0037933177201c2ca4c3b2cc2ef77c2262d`, ветка `cursor/m1-foundation-aa2d`. M1 остаётся частично выполненным; M2 пока не начинается.

## Что подтверждено

Девять транспортных тестов `src/lib/remcard-proxy.test.ts` повторно выполнены на отдельном checkout, все прошли. Команда использовала имеющийся локальный runner `tsx --test`; тесты обращались к локальному stub-серверу, не к production. Повторная полная сборка приложения в этой проверке не выполнялась.

По коду подтверждены удаление production-default, отсутствие запросов при ненастроенном backend, передача PDF как байтов, обработка нескольких cookie и добавление транспортных тестов. Это не доказывает настоящий вход, корректность OAuth callback или сохранение `userId`.

## Две небольшие поправки до интеграции

- **Ответ без тела:** прямой вызов `buildProxyNextResponse` с 204 и 304 воспроизвёл ошибку конструктора `Response`. Для этих статусов передавать `null`, а не пустой `ArrayBuffer`. Добавить отдельные тесты на построение окончательного ответа.
- **Ограничения запросов:** `isAllowedMutatingOrigin(null)` возвращает `true`; широкий auth-regex также разрешает `GET /api/auth/logout`, хотя точечное правило задаёт POST. Для browser BFF выбрать явную политику отказа при отсутствующем/неверном Origin на записи; отдельные небраузерные тестовые обращения не должны служить обходом. Удалить перекрывающий общий auth-regex и определить точные пути/методы после чтения navigator.

Обработка `Location` пока означает передачу заголовка, а не подтверждённый безопасный OAuth-путь. Проверку разрешённых направлений перенаправления и временных cookie завершить после доступа к основному коду.

## Доступ к navigator

Код `karenavedikyan/remcard-navigator` остаётся приватным. Владелец должен разрешить GitHub-интеграции Cursor доступ к этому конкретному репозиторию или использовать локальный Cursor с авторизованной локальной копией рядом.

Наличие доступа у другого инструмента не даёт Cursor доступа автоматически. Не делать navigator публичным, не размещать его архив в этом репозитории и не передавать GitHub-токены в сообщениях.

До выдачи доступа выполнить независимые проверки выше. После выдачи доступа повторить чтение в текущей среде Cursor; если настройки не применились, проверить новую задачу/сессию, не делать вывод по старому отказу.

## Откуда взять URL тестового backend

В просмотренном аккаунте Timeweb на момент проверки есть рабочий backend RemCard и статическое демо кабинета, но отдельного тестового приложения RemCard нет. Рабочий технический домен не является staging; нельзя выдать его за безопасный тестовый backend.

Для минимального первого этапа предлагается запустить navigator локально рядом с новым кабинетом в одной среде разработки:

```text
Кабинет:             http://localhost:3000
Navigator для теста: http://127.0.0.1:3001
База:                отдельная локальная PostgreSQL с синтетическими данными
```

Это предлагаемая конфигурация, а не уже работающие адреса. Установить `REMCARD_API_BASE_URL=http://127.0.0.1:3001` только после фактического запуска и проверки идентичности среды. `localhost` другой машины или другого изолированного агента не подходит.

После доступа к исходникам Cursor должен:

1. Проверить возможность запуска двух процессов и отдельной PostgreSQL в своей среде.
2. Подготовить воспроизводимые команды по фактическим скриптам navigator.
3. Использовать новые локальные секреты и синтетические fixtures; не импортировать production `.env` или дамп клиентов.
4. Проверить, как в основном коде отключаются cron и внешняя доставка, и применить существующие безопасные ограничения.
5. Сначала проверить доступность API и чтение fixture-сессии. Не выдавать это за полный вход через внешнего провайдера.
6. Проверить требования настоящего входа отдельно: callback, HTTPS при необходимости, тестовая конфигурация провайдера. Не разрешать все интеграции только ради одного callback.

Если среда Cursor не поддерживает локальный backend/БД, остановиться с точной причиной. Следующий вариант: отдельно согласованный изолированный сервер и БД с тестовыми данными. Платные ресурсы не создавать автоматически; бюджет статического демо не переносится на backend.

Ни localhost-адрес, ни одна проверка `auth/me` сами по себе не закрывают M1. Полная интеграция считается проверенной только после реального разрешённого сценария входа/выхода и подтверждения неизменного `userId`.
