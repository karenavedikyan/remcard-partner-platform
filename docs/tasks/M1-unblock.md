## Доступ к основному коду

`karenavedikyan/remcard-navigator` является приватным репозиторием. Доступ ассистента к нему не передаётся автоматически среде Cursor.

Предпочтительный способ снять блокер: владелец разрешает GitHub-интеграции Cursor читать этот конкретный репозиторий, после чего Cursor проверяет доступ в своём окружении. Для локального Cursor допустимо открыть рядом локальную копию navigator под уже авторизованной учётной записью владельца.

Не делать navigator публичным и не копировать его полный код, историю, рабочие конфигурации или данные в этот публичный репозиторий ради обхода доступа. Не просить токен в сообщении, не добавлять его в URL клонирования, README, команды отчёта или Git.

После получения доступа проверить `main` и релевантный diff относительно `e6696a44da93e8e1f2bee26d21c3e0f48ee5cbb7`. Затем исправить REUSE-MAP по исходникам, а не по наличию HTTP 401/405.

В частности, предположительные `/api/store/certificate/issue` и `/api/store/certificate/list` в текущей карте не считать подтверждёнными маршрутами. По исходной проверке создание и список обслуживал `src/app/api/store/certificate/route.ts`; актуальные методы и параметры нужно сверить с кодом. Не угадывать модель `ProProfile`, тип авторизации или API по названию.

## Прототип: доступные исходные материалы

Для визуальной части опубликованное статическое демо отдаёт CSS и собранный JS. Проверка содержимого после отчёта Cursor уточнила первоначальную проверку HTTP-кодов: успешный HTTP 200 не гарантирует, что адрес отдельного модуля действительно содержит JS.

- [Основные стили](https://pro.remcard.ru/style.css).
- [Стили сценариев](https://pro.remcard.ru/workflows.css).
- [Стили сертификата](https://pro.remcard.ru/certificate.css).

Адреса `cabinet.js`, `prof-program.js`, `prof-profile.js`, `prof-negotiation.js` и `prof-recommendations.js` не использовать как подтверждённые исходные модули: опубликованная сборка может возвращать по ним HTML через SPA fallback. Проверять Content-Type и фактическое содержимое; изучать зависимости, действительно присутствующие в сборке.

Это реальный источник визуального эталона, а не обязательство перенести всю демонстрационную функциональность. Читать необходимые импорты из исходных файлов, не выдумывать имена остальных модулей.

Для воспроизводимости сохранить SHA-256 и URL использованных материалов в документации. Не считать HTTP ETag или дату CSS коммитом исходников. При необходимости сохранять минимальные визуальные референсы отдельно от runtime, без подключения демонстрационных расчётов к рабочему приложению.

Публичная сборка не является готовой библиотекой React-компонентов. Перенос разметки и стилей в React является адаптацией интерфейса; перенос бизнес-логики демо не нужен.

## Исправления каркаса до проверки входа

Ниже результаты чтения кода текущей ветки, не доказательство воспроизведённого production-инцидента.

### Безопасное окружение

- В `src/lib/config.ts` и `.env.example` рабочий `https://remcard.ru` сейчас задан как backend по умолчанию. Удалить production-default: без явно настроенного разрешённого тестового origin не выполнять сетевые запросы.
- Стартовый экран вызывает `getAuthMeServer()` при загрузке. Без конфигурации показывать «Тестовый backend не подключён», а не обращаться к рабочему сайту автоматически.
- Не создавать миграции/данные/сессии на production. Перед любым seed или тестом проверять allowlist тестовой БД и среды; если идентичность среды неясна, остановиться.
- `REMCARD_BFF_SECRET` объявлен, но сам по себе не защищает прокси. Не считать наличие переменной работающей проверкой; убрать неиспользуемую переменную либо отдельно определить её реальную необходимость без нового механизма аутентификации.

### Корректность прокси

- `upstream.text()` нельзя использовать для PDF и других бинарных ответов. Передавать байты или поток, сохраняя тип и необходимые заголовки.
- Сейчас `redirect: manual`, но `Location` не передаётся клиенту. После изучения реального auth flow определить безопасную обработку redirect/callback и запретить произвольные внешние адреса.
- Передавать несколько `Set-Cookie` раздельно; проверить Path, Domain, Secure, SameSite и удаление cookie при logout. Не расширять область cookie вслепую.
- Не пересылать все cookie браузера upstream автоматически. После проверки основного auth-кода разрешить только нужные имена, включая временные OAuth-cookie, если они используются.
- Текущие широкие префиксы `/api/pro/` и `/api/store/` не являются точным списком PROF-возможностей. Разрешать проверенные комбинации пути и метода; проверять нормализованный путь и запретить обход через закодированные сегменты/`..`.
- Записывающие запросы требуют локальной проверки origin/CSRF в дополнение к серверным правам upstream. Серверный прокси не отменяет эти проверки.
- Сохранить `Cache-Control: no-store` для персональных ответов; корректно обработать 204/304, JSON, ошибки и таймауты. Не выводить сырой upstream-ответ с потенциальными внутренними данными пользователю.

### Проверка сессии

- `getAuthMeServer()` сейчас вызывает сервер без cookie текущего запроса. Ответ `user: null` не доказывает, что авторизованный пользователь будет распознан.
- После чтения auth-кода передавать разрешённые session-cookie для SSR или использовать согласованный клиентский путь проверки. Не передавать токен через URL, localStorage или публичную переменную.
- Разделить проверки транспорта, получения cookie, узнавания существующего `userId` и полного входа через провайдера. Успех одной не означает успех остальных.
- Моки помогают проверить прокси, но не подтверждают настоящий вход.

## Тестовые данные и среда

Не требуются реальные клиентские данные или копия рабочей БД. После доступа к navigator подготовить небольшой синтетический набор в изолированной локальной/тестовой PostgreSQL, используя фактическую схему и ограничения.

Достаточно компании-продавца, поддерживаемого сотрудника, PROF, клиента, партнёрства и категорий. В M1 не создавать реальные покупки и не отправлять сообщения; внешнюю доставку и cron отключить.

Не вводить production-доступный обход авторизации ради тестов. Fixture-сессия может проверить серверную проверку существующего пользователя, но не считается прохождением внешнего входа.

Для полного теста провайдера отдельно нужны подтверждённые URL тестового backend и callback, а при необходимости отдельная конфигурация тестового провайдера. Получать секреты только через защищённые настройки среды, не через этот репозиторий или переписку.

Если изолированная среда ещё не предоставлена, описать минимальную локальную конфигурацию и требования к ней. Не создавать платные ресурсы и не подключаться к production в качестве замены.

6. Проверить настоящий вход/выход и сохранение `userId` в разрешённом тестовом контуре.
7. Обновить STATUS и REUSE-MAP; открыть PR для проверки, но не сливать и не публиковать автоматически.
