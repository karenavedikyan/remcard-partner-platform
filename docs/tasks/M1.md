Целевой репозиторий уже создан: `karenavedikyan/remcard-partner-platform`. Повторно создавать репозиторий или переносить разработку кабинета в основной проект не нужно.

### Подключение существующего backend

Рекомендуемый минимальный вариант: новый интерфейс использует существующие API RemCard. Отдельный репозиторий не означает отдельную копию пользователей, финансовой логики или рабочей базы.

Проверить в тестовом окружении:

- вход и регистрацию на отдельном origin с сохранением существующего `userId`;
- cookie, callback, выход, истечение сессии и серверные проверки;
- CSRF/origin-проверки изменяющих запросов;
- действующие полномочия компании, PROF и поддерживаемого сотрудника;
- ограничения API при вызове из нового кабинета.

Не считать cookie основного домена автоматически доступной на поддомене. Повторный вход допустим, создание дублирующего аккаунта для действующего пользователя не является решением.

Если нужны серверный посредник, настройка callback или небольшая адаптация основного backend, описать точные минимальные изменения и причины. Не выполнять их без отдельного согласования.

Не создавать автоматически новый универсальный API, собственный SSO, новую БД или второй обработчик начислений. Не отключать защиту, не расширять доступ ради успешного запроса и не передавать серверные секреты браузеру.

### Локальная основа нового проекта

После проверки доступности источников подготовить минимальный каркас в этом репозитории:

- совместимый с существующим проектом стек без попутного массового обновления зависимостей;
- базовая структура приложения и подключение дизайн-токенов/необходимых компонентов утверждённого прототипа;
- технический стартовый экран без фиктивных покупателей, балансов или финансовых действий;
- клиент подключения к API с безопасной конфигурацией окружения;
- `.env.example` только с именами переменных и безопасными заглушками;
- `.gitignore`, исключающий секреты, рабочие `.env`, дампы, зависимости и временные файлы;
- `docs/SCOPE.md`: границы первого выпуска и отложенные возможности;
- `docs/REUSE-MAP.md`: карта экранов, API и фактических ограничений;
- `docs/STATUS.md`: выполненное, SHA источников, проверки, блокеры и следующий небольшой шаг.

Не копировать весь основной репозиторий, его историю или серверные зависимости в публичный проект. Переносить только необходимые разрешённые к публикации материалы; при сомнении в правах на материал остановить его публикацию и уточнить.

## Что не делать в M1

- Не реализовывать все экраны PROF: M1 подготавливает основу и способ подключения.
- Не добавлять новые проценты, шаблоны условий, массовые приглашения, CRM, аналитику или способы подтверждения выплат.
- Не считать визуальное наличие функции в прототипе разрешением расширить первый выпуск.
- Не переносить демо-данные и frontend-расчёты прототипа как рабочую бизнес-логику.
- Не создавать второй кошелёк, финансовый журнал или копию пользователей.
- Не менять основной сайт, production-БД, DNS, домен или действующее демо.
- Не создавать платные ресурсы и не отправлять реальные приглашения, сообщения, покупки или выплаты.
- Не публиковать секреты, персональные данные, дампы или внутренние отчёты аудита.

Репозиторий публичный. Последующий перевод в приватный не должен использоваться как основание для публикации чувствительных материалов сейчас.

## Проверки и критерии завершения

- Есть минимальная отдельная локальная основа, которая собирается и запускается по инструкции.
- Понятно, какие части дизайна взяты из прототипа и где получены исходники.
- Каждый основной сценарий сопоставлен с существующим API и серверными правами.
- В тестовом контуре проверен вариант сессии для нового кабинета; действующий пользователь не дублируется.
- Все необходимые изменения основного backend перечислены, но не применены самовольно.
- Каркас не выполняет фоновые production-запросы, не запускает реальные cron и уведомления.
- Новые функции, не поддержанные рабочим сайтом, вынесены в backlog, а не изображены работающими.
- Проверен diff на секреты и посторонние материалы.

Если нет исходников прототипа, доступа к основному коду или тестового backend, указать конкретный блокер и выполнить независимую часть. Вход, проверенный только с моками, не считается подтверждённой интеграцией; задача в таком случае имеет статус «частично выполнено / заблокировано», а не «готово».
